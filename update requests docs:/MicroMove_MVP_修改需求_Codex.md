# MicroMove Web MVP 修改需求（供 Codex 执行）

> **任务目标**：在现有 `micro_movement_codex` Web MVP 基础上，把需求文档中已经明确确定的修改直接做到 MVP 里，使修改后的 MVP 成为后续 App V1 的页面与交互参考版本。
> **原则**：本文件只写“本轮要实现的最终状态”，不保留“旧版 → 新版”的批注历史。未明确要求修改的现有功能、动作数据、推荐逻辑和页面不要擅自重构。

---

## 0. 开发基准与边界

### 0.1 以现有项目为基准
直接修改当前 `micro_movement_codex` 项目，不另起一套页面。

当前核心文件主要包括：

- `src/App.tsx`：主要页面和交互
- `src/data/exercises.ts`：动作数据、动作说明、图片路径、左右动作分组
- `src/session.ts`：动作推荐、Session 生成、左右动作连续逻辑
- `src/storage.ts`：本地数据保存
- `src/copy.ts`：产品文案
- `public/exercise-covers/`：动作卡片 / 跟练封面
- `public/exercise-demo-pages/`：动作示范原图

### 0.2 本轮明确不做

以下内容不要实现，也不要自行发挥：

1. **IP / 小电池角色设计**
2. **“声音-待完善”中的真实声音功能**
   - 点击按钮振动效果
   - 每个动作的一句话语音包
   - 倒计时滴滴声
3. **起身小任务**
4. **养娃娃 / 奖励养成机制**
5. **“动作库 Tab 优化版-待完善”的整体二级导航重构**
6. 任何新的社交、商城、复杂算法或没有在本文件中确认的功能

> “我的”页面可以按照参考样图保留声音/振动设置的**视觉区域**，但本轮不要实现上述尚未定稿的真实音频、语音或振动行为。

### 0.3 Web MVP 与原生 App 能力的边界

本轮目标是把 **Web MVP 做成后续 App 的产品原型参考**。

- 可以在 Web 中实现的页面、状态、交互、本地保存：直接实现。
- **系统级后台推送 / 原生桌面小组件**：本轮不要求真正接入系统能力。
- 但“我的”页面中的**提醒设置入口、提醒时间设置、增加小组件入口及对应 UI**需要做出来，作为 App 开发参考。
- 不要为了模拟原生能力大规模改造现有 Web 技术栈。

本轮**不做**“动作库 Tab 优化版-待完善”中整套横向二级分类重构。

## 2.3 收藏排序

点击爱心收藏后：

1. 动作进入收藏状态。
2. 收藏的动作自动排到动作列表前面。
3. **最新收藏的动作排在最上方。**
4. 多个收藏动作按“最近收藏 → 较早收藏”排序。
5. 取消收藏后，该动作回到普通动作排序逻辑。
6. 收藏状态和收藏顺序需要本地保存，刷新页面后仍保留。

## 2.4 默认动作时长

所有动作默认跟练时长统一改为：

- **单方向 / 非对称动作：15 秒**
- **左右对称动作：每侧 15 秒**
- **前后 / 两方向对称动作：每个方向 15 秒**

注意：对称动作不是“总共 15 秒”，而是**每侧 / 每方向各 15 秒**。

动作库卡片、动作详情、跟练逻辑中出现的默认时长保持一致，不再残留默认 30 秒的旧逻辑。

# 4. 所有跟练的统一交互

## 4.1 跟练前：5 秒准备阶段

参考：

![5秒准备参考](references/07_跟练前_5秒准备参考.png)

无论从动作库进入单个动作，还是从首页进入完整动作组：

当前参考：

![正式跟练页当前参考](references/08_正式跟练页_当前参考.png)

在现有跟练页基础上修改：

### 顶部

1. `动作 2 / 2` 这类动作进度信息移动到**页面顶部中间**。
2. 左上角保留返回箭头。
3. 给返回箭头增加清晰的按钮边框 / 点击区域。
4. 删除返回箭头旁的“回动作库”等文字。

### 动作图片和倒计时

- 动作名称加入后，图片和倒计时整体适当下移；

- 暂停 / 继续
- 跳过
- 重来 / 当前已有控制

若未被上述要求明确删除，则保持原有逻辑，不要无故重构。

## 4.7 有效运动记录与打卡判定

跟练记录、今日累计时长、日历打卡和连续天数必须统一使用以下有效完成规则：

1. 完整动作组只有在所有动作都完整跟练结束后，才生成有效完成记录。
2. 从动作库进入的单个动作，只有完整跟练结束后才生成有效完成记录；对称动作需完成所有方向 / 两侧。
3. 用户中途退出时不生成有效完成记录，也不增加今日累计、日历打卡或连续天数。
4. 被跳过的动作不计入有效运动时长；只要存在未完整完成的计划动作，该次动作组不计为有效完成。
5. 全部跳过时不进入有效完成状态，不写入有效完成记录。
6. 今日累计只汇总当日有效完成记录的实际有效时长。
7. 日历打卡以当日是否存在至少一条有效完成记录为准。
8. 连续天数按“有效完成日”去重计算，同一自然日完成多次也只计一天。

### D. 提醒

“我的”页面加入提醒入口与设置。

提醒设置参考：

![提醒设置参考](references/11_提醒设置_参考.png)

基础规则：

- 提醒开关
- 默认可提供约 **11:00**、**16:00** 的提醒时间
- 用户可以自定义提醒时间

提醒文案风格：

- 不责备
- 不命令
- 不制造连续打卡压力
- 强调低门槛
- 强调恢复感

可轮换的现有文案：

1. 坐了一阵啦，起来回个电？30 秒就够。
2. 这段忙完了吗？刚好起来动一下。
3. 给肩颈换换状态吧。一分钟也可以。
4. 有点没电了吗？动一下再继续。
5. 不用完成一整套。现在动 30 秒就很好。

> Web MVP 中完成提醒设置页面、时间设置、本地保存和产品交互即可。不要为了本轮任务自行搭建复杂后台推送系统。

- 不要求实现真正的 iOS / Android 原生桌面小组件。

### F. 声音与振动区域

如果按照样图保留该区域：

- **不要实现**文档中“声音-待完善”列出的真实语音包、倒计时声音、点击振动等行为。

## 6.10 我的动作组管理

动作库 Tab 中的“我的动作组”需支持对已保存动作组进行完整管理：

1. 点击已保存动作组后，进入动作组预览 / 编辑页。
2. 用户可以增加、删除动作，并调整总时长或单个动作时长。
3. 用户可以重新命名动作组。
4. 所有调整先保留为当前页面的临时草稿，不得在调整过程中自动覆盖原数据。
5. 只有用户主动点击“保存修改”后，才用当前草稿覆盖原动作组的名称、动作顺序与单动作时长。
6. 未点击“保存修改”就返回时，放弃临时调整，原动作组数据保持不变。
7. “删除动作组”必须先展示二次确认；仅在用户再次确认后删除并更新本地持久化数据。
8. 继续复用现有 `SavedMovementGroup` 与 localStorage 保存方案，不新增后端。
